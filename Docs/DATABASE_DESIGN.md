**Document:** `DATABASE_DESIGN.md`\
**Version:** 1.0\
**Status:** Proposed baseline for MVP\
**Product:** SteamScoop --- *Understand Games Through Data.*

------------------------------------------------------------------------

## 1. Purpose and scope

This document defines the logical and physical database design for
SteamScoop: entity relationships, PostgreSQL tables and columns,
constraints, indexes, migration strategy, and data dictionary.

The design supports:

-   Multi-game Steam catalog and controlled game indexing.
-   Historical sampled review collection and weekly incremental
    synchronization.
-   Idempotent ingestion, cursor checkpoints, retry/recovery, and
    auditability.
-   Versioned sentiment, aspect-based sentiment analysis (ABSA), and
    topic-model outputs.
-   Aggregated game intelligence and temporal analysis.
-   Optional user accounts, research workspaces, saved analyses, and
    asynchronous exports.
-   Administrative operations and operational traceability.

The design assumes a **modular monolith** with FastAPI, PostgreSQL,
Redis, and Celery workers. PostgreSQL is the system of record. Redis is
not authoritative for job state, checkpoints, or collection progress.

### 1.1 Design principles

1.  **Raw source data is separated from derived intelligence.** Steam
    review content and model predictions have different lifecycles.
2.  **Every model output is versioned.** A prediction must be traceable
    to a model version and pipeline run.
3.  **Collection is resumable and idempotent.** A review is uniquely
    identified per game by its Steam review ID.
4.  **Operational state is durable.** Jobs, batches, checkpoints, and
    pipeline runs are persisted in PostgreSQL.
5.  **Public traffic cannot trigger arbitrary ingestion.** Collection is
    controlled by the scheduler and authorized administrative workflows.
6.  **Store only what the product needs.** Avoid retaining Steam account
    identifiers and unnecessary author/device metadata.
7.  **Use UTC for persisted timestamps.** Convert to local time (WIB) at
    the presentation layer.
8.  **Prefer relational integrity.** Use foreign keys and explicit join
    tables instead of opaque JSON relationships.
9.  **Keep JSONB for variable source payloads and configuration only.**
    Core queryable attributes remain typed columns.
10. **Design for PostgreSQL first.** Do not add a separate warehouse or
    search engine until measured requirements justify it.

## 2. Database conventions

  -----------------------------------------------------------------------
  Concern                             Convention
  ----------------------------------- -----------------------------------
  Database                            PostgreSQL

  Primary keys                        `UUID`, generated by the
                                      application or `gen_random_uuid()`

  Steam identifiers                   `BIGINT` where numeric; `appid` is
                                      a positive `INTEGER`

  Timestamps                          `TIMESTAMPTZ`, stored in UTC

  Date-only values                    `DATE`

  Language                            BCP 47 / ISO language tag where
                                      available, e.g. `en`, `id`, `zh-cn`

  Currency                            ISO 4217 code, e.g. `USD`, `IDR`

  Monetary values                     `NUMERIC`, never floating-point

  Percentages / confidence            `NUMERIC` or `DOUBLE PRECISION`
                                      with range checks

  Boolean                             `BOOLEAN NOT NULL` when the value
                                      is required

  Flexible payloads                   `JSONB`, only when structure is
                                      genuinely variable

  Naming                              `snake_case`, singular table names

  Soft deletion                       Avoid by default; use explicit
                                      status or archival fields where
                                      needed

  Deletion behavior                   Prefer `RESTRICT`; use `CASCADE`
                                      only for owned child records

  Enum strategy                       `VARCHAR` plus `CHECK` for MVP;
                                      PostgreSQL enum only for stable,
                                      rarely changed sets
  -----------------------------------------------------------------------

### 2.1 Common conventions

-   All mutable business tables should have `created_at` and
    `updated_at` where applicable.
-   `updated_at` is maintained by the application or a database trigger;
    choose one strategy consistently.
-   Immutable event/result tables may use only `created_at`.
-   Avoid nullable columns unless `NULL` has a clear semantic meaning.
-   Distinguish "unknown", "not collected", and "not applicable"; do not
    overload empty strings.
-   Do not store calculated totals if they can be reliably derived,
    except for explicitly versioned snapshots or performance aggregates.

                                                                                    payload for
                                                                                    debugging/reprocessing

  `first_collected_at`              TIMESTAMPTZ                    No `now()`       First successful
                                                                                    collection time

  `last_seen_at`                    TIMESTAMPTZ                    No `now()`       Most recent time
                                                                                    observed from Steam

  `created_at`                      TIMESTAMPTZ                    No `now()`       Internal creation time

  `updated_at`                      TIMESTAMPTZ                    No `now()`       Internal update time

**Constraints** - `UNIQUE (game_id, steam_review_id)` --- idempotency
key. - `FOREIGN KEY (game_id) REFERENCES game(id) ON DELETE RESTRICT`. -
`CHECK (steam_review_id > 0)`. -
`CHECK (votes_up >= 0 AND votes_funny >= 0 AND comment_count >= 0)`. -
Playtime columns must be `NULL` or non-negative. -
`CHECK (weighted_vote_score IS NULL OR weighted_vote_score >= 0)`. -
`review_text` must not be an empty string after normalization; preserve
legitimate short reviews.

**Indexes** - Unique B-tree `(game_id, steam_review_id)`. - B-tree
`(game_id, steam_created_at DESC)` for game timelines. - B-tree
`(game_id, voted_up, steam_created_at DESC)` for filtered review
browsing. - B-tree `(game_id, language, steam_created_at DESC)` if
language filtering is exposed. - Optional GIN full-text index on a
generated `tsvector` only after validating multilingual search
requirements. PostgreSQL's default English configuration is not
sufficient for every review language. - Avoid indexing the full
`review_text` with a generic GIN trigram index until query patterns and
storage cost are measured.

**Privacy and retention** - Do not persist SteamID, profile URL, avatar,
account name, or unnecessary author identifiers. - If raw payload is
retained, strip author/account fields before persistence. - Document a
retention policy for `source_payload`; it may be disabled or pruned
after successful normalization.

## 6. Ingestion and checkpoint tables

### 6.1 `ingestion_job`

A durable logical collection job. A job may consist of multiple API page
requests/batches.

  -----------------------------------------------------------------------------------------------------
  Column                   Type                       Null Default                   Description
  ------------------------ ------------- ----------------- ------------------------- ------------------
  `id`                     UUID                         No generated                 Job primary key

  `game_id`                UUID                         No ---                       Target game

  `job_type`               VARCHAR(24)                  No ---                       `historical` or
                                                                                     `incremental`

  `status`                 VARCHAR(20)                  No `queued`                  Job lifecycle
                                                                                     state

  `source_api`             VARCHAR(80)                  No `steam_user_reviews_v1`   Source adapter
                                                                                     identifier

  `request_config`         JSONB                        No `{}`                      Filters, language,
                                                                                     sample policy, and
                                                                                     requested range

  `requested_by_user_id`   UUID                        Yes ---                       Admin actor, null
                                                                                     for scheduler

  `scheduled_at`           TIMESTAMPTZ                 Yes ---                       Intended execution
                                                                                     time

  `started_at`             TIMESTAMPTZ                 Yes ---                       Actual start

  `finished_at`            TIMESTAMPTZ                 Yes ---                       Terminal time

  `reviews_seen`           BIGINT                       No `0`                       Number of source
                                                                                     review records
                                                                                     examined

  `reviews_inserted`       BIGINT                       No `0`                       New review rows

  `reviews_updated`        BIGINT                       No `0`                       Existing review
                                                                                     rows updated

  `pages_processed`        INTEGER                      No `0`                       Completed API
                                                                                     pages

  `retry_count`            INTEGER                      No `0`                       Number of retries

  `error_code`             VARCHAR(80)                 Yes ---                       Stable
                                                                                     machine-readable
                                                                                     error

  `error_message`          TEXT                        Yes ---                       Sanitized
                                                                                     operational
                                                                                     message

  `created_at`             TIMESTAMPTZ                  No `now()`                   Creation time

  `updated_at`             TIMESTAMPTZ                  No `now()`                   Last update
  -----------------------------------------------------------------------------------------------------

**Constraints** -
`FOREIGN KEY (game_id) REFERENCES game(id) ON DELETE RESTRICT`. -
`FOREIGN KEY (requested_by_user_id) REFERENCES user(id) ON DELETE SET NULL`. -
`CHECK (job_type IN ('historical','incremental'))`. -
`CHECK (status IN ('queued','running','retrying','succeeded','partial','failed','cancelled'))`. -
All counters are non-negative. -
`finished_at IS NULL OR started_at IS NOT NULL`. -
`finished_at IS NULL OR finished_at >= started_at`.

**Indexes** - B-tree `(status, scheduled_at)` for queue/recovery
scans. - B-tree `(game_id, created_at DESC)` for per-game job history. -
Partial unique index to prevent multiple active jobs for the same game
and job type, if product policy allows only one active job:
`UNIQUE (game_id, job_type) WHERE status IN ('queued','running','retrying')`.
If concurrent jobs are needed later, replace this with an explicit
job-coordination policy.

### 6.3 `collection_checkpoint`

Durable progress for one game and one collection stream. The stream key
distinguishes historical sampling from incremental updates and allows
future language/filter partitions.

  -----------------------------------------------------------------------------------------------------
  Column                     Type                        Null Default       Description
  -------------------------- -------------- ----------------- ------------- ---------------------------
  `id`                       UUID                          No generated     Checkpoint primary key

  `game_id`                  UUID                          No ---           Target game

  `stream_key`               VARCHAR(120)                  No ---           Stable stream identity,
                                                                            e.g. `historical:all:all`

  `collection_mode`          VARCHAR(16)                   No ---           `historical` or
                                                                            `incremental`

  `cursor`                   TEXT                         Yes ---           Current Steam cursor

  `watermark_at`             TIMESTAMPTZ                  Yes ---           Last fully committed
                                                                            incremental watermark

  `last_successful_job_id`   UUID                         Yes ---           Last successful job

  `last_success_at`          TIMESTAMPTZ                  Yes ---           Last successful completion

  `status`                   VARCHAR(16)                   No `idle`        Checkpoint state

  `metadata`                 JSONB                         No `{}`          Bucket, sample target, and
                                                                            policy details

  `created_at`               TIMESTAMPTZ                   No `now()`       Creation time

  `updated_at`               TIMESTAMPTZ                   No `now()`       Last update
  -----------------------------------------------------------------------------------------------------

**Constraints** -
`FOREIGN KEY (game_id) REFERENCES game(id) ON DELETE RESTRICT`. -
`FOREIGN KEY (last_successful_job_id) REFERENCES ingestion_job(id) ON DELETE SET NULL`. -
`UNIQUE (game_id, stream_key)`. -
`CHECK (collection_mode IN ('historical','incremental'))`. -
`CHECK (status IN ('idle','running','paused','error'))`. - A watermark
advances only after the complete requested incremental range has been
committed.

**Indexes** - Unique B-tree `(game_id, stream_key)`. - B-tree
`(status, updated_at)` for recovery monitoring.

**Transaction invariant** For each accepted page, persist review
upserts, the `ingestion_batch` record, and the next cursor/checkpoint in
one database transaction. If the transaction fails, none of these
changes should be committed. This prevents a cursor from moving ahead of
data that was not stored.

## 11. Indexing strategy

### 11.1 Index design rules

-   Every foreign key used in joins or deletion checks should have an
    appropriate child-side index. PostgreSQL does not automatically
    create indexes on referencing columns.
-   Unique constraints create their own unique indexes; do not duplicate
    them.
-   Build indexes from actual API query patterns, not from every column.
-   Use partial indexes for active/queued records.
-   Use composite indexes with equality predicates first, followed by
    sort/range columns.
-   Validate query plans with `EXPLAIN (ANALYZE, BUFFERS)` against
    realistic data volumes.
-   For large tables, use `CREATE INDEX CONCURRENTLY` in an operational
    migration where supported; it cannot run inside a normal transaction
    block.
-   Revisit index usage and write amplification as the review corpus
    grows.

### 11.3 Review table growth

The review table is expected to be the largest table. Begin with a
normal PostgreSQL table and benchmark before partitioning. Consider
monthly range partitioning by `steam_created_at` only when: - table size
and maintenance operations justify it; - queries consistently include
time predicates; - unique-key requirements are redesigned to include the
partition key, because PostgreSQL partitioned-table unique constraints
have partition-key requirements.

Do **not** partition in the first migration merely as a precaution.
Partitioning increases migration and uniqueness complexity.

## 12. Data integrity and business invariants

1.  A Steam review is unique within a game by
    `(game_id, steam_review_id)`.
2.  Re-fetching a review updates the existing row; it does not create a
    duplicate.
3.  Steam recommendation (`voted_up`) and model sentiment
    (`sentiment_prediction.label`) are separate concepts.
4.  Every prediction references a review, model version, and pipeline
    run.
5.  Model versions are immutable; new model behavior creates a new
    version.
6.  A topic belongs to a specific topic-model version.
7.  A collection checkpoint is scoped by `(game_id, stream_key)`.
8.  Cursor progress, review upserts, and batch records commit atomically
    per page.
9.  An incremental watermark advances only after the full requested
    interval is committed.
10. Public analytics requests never enqueue ingestion jobs.
11. A game may be disabled from public discovery without deleting its
    historical data.
12. An export must enforce authorization, row limits, and expiry
    independently of UI controls.
13. Aggregate records are rebuildable derived data and must record their
    model/version key.
14. All timestamps are stored in UTC.
15. Raw source payloads and operational error messages must be scrubbed
    of credentials and unnecessary personal data.

## 13. Migration strategy

Use **Alembic** for schema versioning. Every migration must be committed
to source control and reviewed.

### 13.1 Migration principles

-   One migration should represent one coherent schema change.
-   Migrations must be deterministic and safe to run in a fresh
    environment.
-   Use explicit names for constraints and indexes.
-   Prefer expand--migrate--contract for changes to columns used by a
    live application.
-   Do not silently rewrite historical model predictions during a schema
    migration.
-   Data backfills should be bounded, restartable, and observable.
-   Large index builds should be planned separately from transactional
    DDL when needed.
-   Never make application startup responsible for automatically
    applying production migrations.

### 13.3 Safe migration examples

**Adding a nullable column (expand):** 1. Add the nullable column. 2.
Deploy application code that can read both old and new states. 3.
Backfill existing rows in batches. 4. Add validation/constraint. 5.
Deploy code that writes the new column. 6. Make it `NOT NULL` only after
verifying there are no null rows.

**Renaming a column:** 1. Add the replacement column. 2. Dual-write
temporarily. 3. Backfill. 4. Switch reads. 5. Remove the old column in a
later release.

**Adding an index to a live large table:** - Use a concurrent index
build where appropriate. - Ensure the migration runner handles the fact
that concurrent index creation cannot run inside a transaction block. -
Verify index validity after the operation.


### 13.5 Migration quality gates

Before merge: - Fresh database can migrate to `head`. - Upgrade from the
previous release succeeds. - Constraints reject invalid fixtures. -
Foreign keys and indexes exist with expected names. - Backfill is
idempotent and can resume. - Downgrade is tested where practical;
destructive production rollback should generally use a forward fix. -
Application and worker versions are compatible with the expanded schema
during rolling deployment.

## 16. Operational query patterns

### 16.1 Idempotent review upsert

Use `(game_id, steam_review_id)` as the conflict target. Update only
source fields that may change, and update `last_seen_at`. Do not replace
the internal primary key.

``` sql
INSERT INTO review (
    id, game_id, steam_review_id, language, review_text, voted_up,
    votes_up, votes_funny, steam_created_at, steam_updated_at,
    first_collected_at, last_seen_at, created_at, updated_at
)
VALUES (
    gen_random_uuid(), :game_id, :steam_review_id, :language, :review_text,
    :voted_up, :votes_up, :votes_funny, :steam_created_at, :steam_updated_at,
    now(), now(), now(), now()
)
ON CONFLICT (game_id, steam_review_id)
DO UPDATE SET
    language = EXCLUDED.language,
    review_text = EXCLUDED.review_text,
    voted_up = EXCLUDED.voted_up,
    votes_up = EXCLUDED.votes_up,
    votes_funny = EXCLUDED.votes_funny,
    steam_updated_at = EXCLUDED.steam_updated_at,
    last_seen_at = now(),
    updated_at = now();
```

In production, compare tracked fields before updating to avoid
unnecessary row churn. Populate all mapped source fields consistently.

### 16.2 Current sentiment for one game's reviews

``` sql
SELECT
    r.id,
    r.steam_created_at,
    r.voted_up,
    sp.label AS model_sentiment,
    sp.confidence
FROM review AS r
LEFT JOIN sentiment_prediction AS sp
    ON sp.review_id = r.id
   AND sp.is_current = TRUE
WHERE r.game_id = :game_id
ORDER BY r.steam_created_at DESC
LIMIT :limit OFFSET :offset;
```

For large datasets, prefer keyset pagination over large offsets.

### 16.3 Weekly aggregate lookup

``` sql
SELECT *
FROM game_analytic
WHERE game_id = :game_id
  AND period_type = 'week'
  AND model_version_key = :model_version_key
  AND period_start >= :from_date
  AND period_start < :to_date
ORDER BY period_start;
```

### 16.4 Active ingestion recovery

``` sql
SELECT id, game_id, job_type, status, updated_at
FROM ingestion_job
WHERE status IN ('queued', 'running', 'retrying')
  AND updated_at < now() - interval '30 minutes'
ORDER BY updated_at;
```

A recovery worker must verify lease/ownership and checkpoint state
before re-enqueueing; this query alone is not sufficient to decide that
a worker is dead.

## 17. Open decisions before production

The following are deliberate decisions to finalize during implementation
rather than assumptions hidden in the schema:

1.  **Review retention duration:** define duration and
    deletion/anonymization workflow after policy review.
2.  **Raw payload retention:** decide whether `source_payload` is
    disabled, minimized, or retained briefly.
3.  **Language partitioning:** decide whether collection checkpoints are
    per game only or per language/filter stream; `stream_key` supports
    either.
4.  **Current prediction policy:** define whether one model is globally
    current or current status is scoped by task/model release. If
    multiple active model families are needed, add a prediction
    channel/key.
5.  **Topic assignment cardinality:** decide whether one primary topic
    or multiple topic assignments are exposed.
6.  **Sentiment score formula:** publish exact formula, range, and
    handling of neutral/unclassified records.
7.  **Aggregate model key:** define canonical format for
    `model_version_key` and ensure it identifies the
    sentiment/aspect/topic versions used.
8.  **Research role permissions:** define whether `researcher` is a
    global role or a project-level capability.
9.  **Export storage:** select private object storage and signed URL
    expiry policy.
10. **Review partitioning:** benchmark before introducing partitioning.
11. **Game metadata normalization:** normalize
    genres/developers/publishers only if filtering, deduplication, or
    reporting requires relational facets.
12. **Email identity:** decide whether authentication is password-based,
    external identity provider, or both.

8.  Add research workspace, snapshots, exports, and audit log.
9.  Add indexes based on measured query plans and load tests.

## 19. Final design summary

The SteamScoop database is a PostgreSQL relational model organized
around the lifecycle of a Steam game review:

**Game catalog → review collection → durable ingestion checkpoints →
versioned NLP predictions → analytics aggregates → optional research
workspaces and exports.**

The most important integrity decisions are the unique review key
`(game_id, steam_review_id)`, durable collection state in PostgreSQL,
atomic persistence of review pages and cursors, and explicit provenance
from every prediction to its model and pipeline run.

This schema is a proposed implementation baseline, not a claim that
every optional workspace table must ship in the first public pilot.
Build the core ingestion and intelligence path first; activate identity,
research, and export tables when their corresponding product
capabilities are ready.
